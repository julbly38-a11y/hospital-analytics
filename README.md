# Hospital Analytics (qwerty)

Медична аналітична платформа для лікарні. Next.js + Supabase, схема `lpz` (канонічна модель ЛПЗ). Прод: [nobodyjul.vercel.app](https://nobodyjul.vercel.app).

## Стек

- **Next.js 14** (Pages Router) — фронтенд і API-роути
- **Supabase** (PostgreSQL) — схема `lpz` (канон), проєкт `ubjnztanehqlsrqphdqy`
- **Vercel** — деплой (гілка `qwerty-project-connection-e6mjy9`)

## Змінні оточення (Vercel / `.env.local`)

| Змінна | Призначення |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | URL проєкту Supabase |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Публічний anon-ключ |
| `SUPABASE_SERVICE_KEY` | service_role ключ (лише бекенд) |

## Вхід і кабінети (`public/`)

| Файл | Опис |
|---|---|
| `layout.html` | Слайд-вхід (логін), лікарня визначається за `?org=<ЄДРПОУ>` |
| `entry.html` | Перехідна сторінка після логіну — КПІ лікарні, клінічний блок, чергові лікарі. Терапевтичний блок зараз тестує заміну гістограми хвилястим (area) графіком — WIP, не узгоджено остаточно, хірургічний блок без змін |
| `head-cabinet.html` | Кабінет завідувача — КПІ відділення, Ординаторська, донат "Структура діагнозів", "Перебуває у відділенні" |
| `doctor-cabinet.html` | Кабінет лікаря — свої пацієнти, Ординаторська (колеги по відділенню) і смуга "Чергові лікарі" (той самий шар, що на head-cabinet.html) |

### Доступ власника сайту (`is_owner`) — вхід у будь-яке відділення/лікаря

Акаунт-власник сайту (`app_users.is_owner`, без прив'язки до `empl`/`lpz_empl`) не має власного відділення — за замовчуванням `entry.js` не знає, яку лікарню показувати. Для нього:

- **`entry.html`** без `org_edrpou` у сесії показує тимчасовий перемикач лікарень (`?org=`), той самий патерн, що на `layout.html`
- Клік на відділення в клінічному блоці `entry.html` → `head-cabinet.html?org=&dept=&deptName=` (замість інлайн-розгортки)
- Клік на лікаря в Ординаторській `head-cabinet.html` → `doctor-cabinet.html?org=&dept=&doctor=&doctorName=`
- Ці параметри довіряються **лише** коли сесія підтверджує `me.is_owner === true` (серверне поле з `/api/me`); для звичайного завідувача/лікаря сторінка й далі бере ідентичність тільки з сесії
- Бекенд-виняток поширюється і на PII-ендпоінти (`/api/lpz-department-census`, `/api/lpz-department-icd-blocks[-by-doctor]`) — звичайно вони ігнорують клієнтські `org`/`department` і беруть їх виключно з сесії (`lpz_empl` по email)

## Мобільна версія (WIP)

`shared/layout.css` має `@media (max-width: 768px)` — переводить фіксовану канву 1920×1080 у звичайний стековий document flow (`scale-slide.js` не масштабує нижче цієї ширини). Перевірено наживо лише на `entry.html`; `head-cabinet.html`/`doctor-cabinet.html` ділять той самий CSS-шар, але предметно ще не пройдені.

## `public/old-elements.html`

Галерея готових діаграм/графіків/КПІ-компонентів зі старих проєктів (`hospital-analytics` main, `lsmd`, `lsmd-design-system`) — SVG-рушії (`spark-chart.js`, `dept-pie.js`, `doc-trend.js`, `double-donut.js`, `neuro-cv-pie.js`, `neuro-treemap.js`), React+Recharts компоненти, старий React-прототип дашборду (`public/dashboard/`), прев'ю дизайн-системи (`public/design-preview/`). Усе з тестовими даними, ізольовано від застосунку — довідковий "склад" для поступової адаптації елементів.

### head-cabinet.html — ключові інтерактивні елементи

- **Ординаторська** — hover на лікаря підсвічує його сегменти в донаті; клік — інлайн-розгортка його пацієнтів (лише коли обрано точний день на денній гістограмі)
- **Донат "Структура діагнозів"** (`dept-pie.js`) — топ-5 МКХ-блоків серед тих, хто перебуває у відділенні на обрану дату; клік на сегмент = клік на пацієнта з відповідним діагнозом
- **"Перебуває у відділенні"** — порожнє, доки не обрано конкретний день на денній гістограмі КПІ-графіка (клік на стовпець року/місяця лише перемикає графік, не показує список); клік на пацієнта підсвічує лікаря і повертає відповідний сегмент донату вгору
- **Історія госпіталізацій** — клік на цифру повторних госпіталізацій розгортає всю історію пацієнта по лікарні
- Клік будь-де інде закриває всі відкриті розгортки
