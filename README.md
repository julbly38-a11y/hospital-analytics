# Hospital Analytics (qwerty)

Медична аналітична платформа для лікарні. Next.js + Supabase, схема `lpz` (канонічна модель ЛПЗ). Прод: [nobodyjul.vercel.app](https://nobodyjul.vercel.app).

## Стек

- **Next.js 14** (Pages Router) — фронтенд і API-роути
- **Supabase** (PostgreSQL) — схема `lpz` (канон), проєкт `ubjnztanehqlsrqphdqy`
- **Vercel** — прод `nobodyjul`: деплой **вручну** `vercel --prod --yes` з цієї робочої копії (прив'язана через `.vercel/project.json`); git push на прод не впливає. Функції — регіон `lhr1` (Лондон, `vercel.json`), поруч із базою Supabase (`eu-west-2`); в `iad1` кожен запит до бази йшов через Атлантику

## Вхід і кабінети (`public/`)

| Файл | Опис |
|---|---|
| `layout.html` | Слайд-вхід (логін), лікарня визначається за `?org=<ЄДРПОУ>` |
| `entry.html` | Перехідна сторінка після логіну — КПІ лікарні, клінічний блок, чергові лікарі. Терапевтичний блок зараз тестує заміну гістограми хвилястим (area) графіком — WIP, не узгоджено остаточно, хірургічний блок без змін |
| `head-cabinet.html` | Кабінет завідувача — КПІ відділення, Ординаторська, донат "Структура діагнозів", "Перебуває у відділенні" |
| `doctor-cabinet.html` | Кабінет лікаря — свої пацієнти, Ординаторська (колеги по відділенню) і смуга "Чергові лікарі" (той самий шар, що на head-cabinet.html) |
| `quality.html` | Контроль записів — випадки з помилками, що впливають на оплату НСЗУ (див. нижче) |

Клік на емблему на `entry.html` / `head-cabinet.html` / `doctor-cabinet.html` вмикає фінансовий режим цієї сторінки — див. «Фінансовий режим кабінетів».

### Доступ власника сайту (`is_owner`) — вхід у будь-яке відділення/лікаря

Акаунт-власник сайту (`app_users.is_owner`, без прив'язки до `empl`/`lpz_empl`) не має власного відділення — за замовчуванням `entry.js` не знає, яку лікарню показувати. Для нього:

- **`entry.html`** без `org_edrpou` у сесії показує тимчасовий перемикач лікарень (`?org=`), той самий патерн, що на `layout.html`
- Клік на відділення в клінічному блоці `entry.html` → `head-cabinet.html?org=&dept=&deptName=` (замість інлайн-розгортки)
- Клік на лікаря в Ординаторській `head-cabinet.html` → `doctor-cabinet.html?org=&dept=&doctor=&doctorName=`
- Ці параметри довіряються **лише** коли сесія підтверджує `me.is_owner === true` (серверне поле з `/api/me`); для звичайного завідувача/лікаря сторінка й далі бере ідентичність тільки з сесії
- Бекенд-виняток поширюється і на PII-ендпоінти (`/api/lpz-department-census`, `/api/lpz-department-icd-blocks[-by-doctor]`, `/api/lpz-patient-hospitalizations`, `/api/lpz-case-quality`) — звичайно вони ігнорують клієнтські `org`/`department` і беруть їх виключно з сесії (`lpz_empl` по email)

## Контроль записів (`quality.html`)

Щоденна перевірка епізодів helsi на помилки в записах, через які НСЗУ недоплачує або перераховує оплату. Система епізоди не змінює — лише інформує того, хто може виправити, щоб він виправив сам.

**Нотатка над кожним некоректним епізодом:** адресат і пари підказок по кожному зауваженню:
- **первинна** — що не так і яке правило (`Q_FLAGS[*].rule` у `public/js/quality-notes.js`);
- **вторинна** — деталі з даних самого епізоду (`hints` у таблиці): стан виписки й автор, номер і дати епізоду-накладки, інші діагнози в записі, діагнози з інших епізодів пацієнта тощо.

**Адресат:** лікар, який веде епізод (лікуючий), а для закритих без лікуючого — лікар, що підписав виписку (зіставлення з `lpz_empl` за ПІБ / прізвищем та ініціалами). Якщо лікаря не визначено — завідувач відділення.

**Три сегменти**

| Сегмент | Що містить |
|---|---|
| Відкриті | Пацієнти у відділеннях: помилки, що вже є, і попередження — що стане помилкою, якщо не доповнити до виписки |
| Можна виправити | Закриті з помилками, строк подачі змін ще не минув (найближчі строки — зверху) |
| Вже не виправити | Закриті з помилками, строк минув — фактичні втрати, для аналізу причин |
| Попередження (`warned`, з 21.09.2026) | Закриті лише з попередженнями (немає лікаря, один діагноз, не вказано «Вид травми») — оплату не блокують, помилкою й грошовим ризиком не рахуються, у фінансових показниках — як правильні; зберігаються, бо правила НСЗУ можуть змінитись |

Строк (`fix_deadline`) — 10-й робочий день місяця, наступного за місяцем виписки; у воєнний стан рахуються лише вихідні. **Це припущення за правилами НСЗУ — уточнити з економістом лікарні.**

**Перевірки** (`scripts/helsi_quality_daily.js`)

| Код | Відкриті | Закриті | Суть |
|---|---|---|---|
| `no_primary` | помилка (після 1 доби) | помилка | Немає основного діагнозу |
| `overlap` | помилка | помилка | Той самий пацієнт в іншому епізоді з перетином у часі |
| `no_doctor` | попередження | попередження (з 21.09.2026) | Немає лікуючого лікаря; для закритих — і немає підпису лікаря у виписці |
| `injury_no_external_cause` | попередження | попередження (з 21.09.2026) | Травма (S/T) без заповненого поля «Вид травми» (`injury_type` в об'єкті епізоду) |
| `symptom_primary` | попередження (від 2 діб) | помилка | Основний діагноз — симптом (R) |
| `no_interventions` | попередження (від 2 діб) | помилка | Жодного коду втручання НК 026:2021 ні в «процедурах» (операції), ні в «послугах» (введення ліків, обстеження, фізіотерапія) |
| `single_diagnosis` / `death_single_diagnosis` | попередження (від 2 діб) | `single_diagnosis` — попередження (з 21.09.2026), `death_single_diagnosis` — помилка | Лише один діагноз (окремо — для летальних) |
| `open_too_long` | попередження | — | Відкритий понад 30 діб |
| `discharge_not_registered` | — | помилка | Виписки немає, чернетка, очікує реєстрації, скасована або без події в медкарті |
| `no_disposition` | — | помилка (з 21.09.2026) | Виписка є, а результату лікування (`discharge_disposition`) немає — НСЗУ відмовляє (54 відмови; правило ловить 39 із них, ще 11 без виписки покриває `discharge_not_registered`). Власного грошового ризику не додає (`LOSS_SHARE` = 0) — його вже рахують `nszu_refused` і `discharge_not_registered` |

Втручання в helsi лежать у двох розділах: `case-dashboard/{id}/procedures` — лише операції, `case-dashboard/{id}/services` — решта кодів НК 026:2021. Перевірка лише за «процедурами» давала масові хибні спрацювання в хірургічних відділеннях.

`single_diagnosis` найшумніша — позначка означає «перевірити», а не «помилка».

**Доступ** — спільні правила в `lib/quality-access.js` (для `/api/lpz-case-quality` і `/api/lpz-quality-finance`), лише з сесії: `chief` — уся лікарня, `head` — усі епізоди свого відділення (адресовані йому — першими), `doctor` — епізоди, адресовані йому, власник сайту — `?org=`, а з кабінету чужого відділення чи лікаря — `&dept=` / `&doctor=` (параметрам довіряємо лише для `is_owner`). **Начмеди (`deputy`) поки без доступу** — у `lpz_empl` немає прив'язки заступника до напрямку (терапевтичний/хірургічний).

### Гроші для головного лікаря (`lib/quality-pricing.js`)

Лише головному лікарю й власнику сайту (у будь-якому обсязі) API додає `est_price` і `est_risk`; сторінка показує суми: «ризик» (відкриті), «врятувати», «≤ 3 дн.», «втрачено» — у шапці, за типом зауваження, відділенням, а в кожному епізоді — «правильний випадок ≈ ціна · з помилками ≈ ціна − ризик · втрата ≈ ризик». Лікарі й завідувачі грошей не бачать.

| Що | Джерело | Точність |
|---|---|---|
| Базова ставка 8 735 грн за пролікований випадок (хірургічний пакет і стаціонар без операцій) | Постанова КМУ № 1808 від 31.12.2025, п. 34 | офіційно |
| Інсульт без тромболізису/ендоваскулярних втручань — 15 643 грн; інфаркт без стентування — 25 261 грн | там само, п. 45, п. 49 | офіційно |
| Планова допомога без операцій × 0,8 | там само, п. 36.8 | офіційно |
| Вага групи ДСГ | медіана ваг з додатка 1 (366 груп): операції — 2,12; без операцій — за класом хвороб | орієнтовно (точну групу визначає НСЗУ) |
| Частка втрат за типом помилки | виписку не передано / немає діагнозу / відкритий > 30 діб — 100%, накладка — 50%, немає втручань і симптом — 30%, летальний з 1 діагнозом — 25%; травма без «Виду травми», без лікаря й один діагноз — 0% (доведено `package-validation`, що оплату не блокують; з 18.09.2026) | експертна оцінка |

**Розрахунок НСЗУ по всіх відділеннях (21.09.2026).** Факти й `package-validation` зібрано для всіх виписаних епізодів усіх 13 відділень ЛШМД (з 01.01.2026, 5 статусів; скрипти `collect_lpz_episode_facts.js` / `collect_package_validation.js` тепер беруть усі статуси, повторюють запит при збої мережі; `department: ''` = усі відділення), у ту саму `lpz_episode_facts`. Результат: **4 039 епізодів із реальною ціною з 7 558 (53%)**, сума 66,9 млн грн (стара оцінка для тих самих — 54,4 млн: спецпакети з фіксованим тарифом — інсульт 15 643, інфаркт 25 261, гематологія 148 858, 131 472 — оцінка недооцінювала). 594 випадки — пряма відмова НСЗУ (типи — у `lpz_quality_check_catalog`, profile «усі відділення», коди `nszu_*`; найчастіше: підстава звернення, послуги не як «Діагностичний звіт», недопустима категорія послуги, немає результату лікування, немає всіх послуг у виписці). Пакети: №3 (хірургія, 1 750), №4 (без операцій, 2 135), №47 (одного дня, 122), спецпакети без номера (218).
- **Обмеження 90 днів:** `package-validation` відхиляє епізоди, що почалися понад 90 днів тому («Дата не може бути раніше ніж 90 днів тому») — це ~2 000 епізодів, точної ціни для них через API отримати не можна. Спроба зсунути дати вперед (тривалість та сама) дала ту саму ціну лише у 35 з 40 епізодів, у 5 — іншу або відмову «Некоректна тривалість» (helsi звіряє ще й дати послуг усередині епізоду), тому **зсув дат не використовується**; для таких епізодів лишається орієнтовна оцінка. Раніше 377 таких епізодів травматології були помилково записані як «відмова НСЗУ» — виправлено на «не розраховано».
- **Два режими перегляду на `quality.html` (21.09.2026):** перемикач у правому верхньому полі — «усі епізоди · N» (точні + орієнтовні) і «реальні дані НСЗУ · M» (епізоди з реальною ціною з `package-validation`, ~4 000). Режим фільтрує лічильники, суми, типи зауважень, відділення й список; біля суми кожного епізоду — позначка «розрахунок НСЗУ» / «орієнтовно», під поясненням — покриття («N з M епізодів, ≈ X% суми»). API `/api/lpz-case-quality` віддає для цього `nszu_priced` (кожен епізод), `nszu_priced_total`, `nszu_money_share` (лише для тих, хто бачить гроші). Той самий перемикач є й у кабінетах у фінансовому режимі (`entry`/`head-cabinet`/`doctor-cabinet`): пігулки «усі епізоди · N» / «реальні дані НСЗУ · M» (кількість епізодів у підписах; шапка кабінету — обсяг усієї лікарні, `coverage` у відповіді `/api/lpz-quality-finance`) праворуч від кнопки «Контроль записів» (`utils.js: finBasis`, параметр `?basis=nszu`, перемикання перезавантажує сторінку й зберігається при переході між кабінетами; `/api/lpz-quality-finance?basis=nszu` рахує показники лише за епізодами з розрахунком НСЗУ, список епізодів кабінету фільтрується за `nszu_priced`).
- **Відмова НСЗУ як помилка контролю (`nszu_refused`, 21.09.2026):** `lib/quality-access.js` при читанні таблиці перевірки додає закритим епізодам із `validation_success = false` помилку `nszu_refused` з читабельним текстом відмови у вторинній підказці (558 епізодів; 455 з них не мали жодного іншого нашого зауваження — наші евристики їх не бачили). **Застереження:** 502 з 594 відмов — на виписках, УЖЕ зареєстрованих в ЕСОЗ, тож чи не заплатять за них фактично — не підтверджено (потрібна звірка з виплатами НСЗУ). Тому грошовий ризик 100% (`estimateRisk`) — лише для ще не зареєстрованих виписок (81 епізод); для зареєстрованих відмова лишається помилкою в нотатці без грошового ефекту. Для епізодів із реальною ціною зауваження, які НСЗУ вже врахувало (`no_interventions`, `symptom_primary`, `single_diagnosis`…), ризику не дають — лишаються `discharge_not_registered`, `overlap`, `open_too_long` (їх `package-validation` не перевіряє).
- Незакрито: 98 рядків результату не знайшлись у `lpz_episode_facts` (епізоди, закриті між збором фактів і розрахунком) — довантажити повторним збором фактів.

**Реальна ціна (з 21.09.2026):** для епізодів, що є в `lpz.lpz_episode_facts` з успішним `package-validation` (зараз травматологія), ціна = `adjustment_price / adjustment_coefficient` — повна ціна ДСГ з коефіцієнтами епізоду (ААС, тривалість, множинні операції); підмішується при читанні таблиці перевірки (`readRealPrices` у `lib/quality-access.js`, поле `real_price`, у відповіді API — `est_from_nszu`). Для решти відділень — орієнтовна оцінка нижче. На прогоні 14.09: 903 з 6 893 епізодів мають реальну ціну; їхня сума 12,98 млн проти 13,66 млн за старою оцінкою (−5%).

Ціна епізоду = ставка × вага (× 0,8 для планових без операцій); під ризиком = ціна × найбільша частка серед його зауважень. Для операцій потрібні `operations_count` і `admission_priority` у таблиці.

**Звірка з фактом (14.09.2026).** Відкриті дані НСЗУ — [data.gov.ua, «Оплати суб'єктам господарювання за ПМГ»](https://data.gov.ua/dataset/25a46db9-2f15-4302-9b59-9bd761c80f46), файл `payments_on_contracts_pmg_2026.csv` (поля `legal_entity_edrpou, period_month, package_id, pay_package, …`). ЛШМД за липень 2026: пакети 3/4/5/6 (за сумами — хірургічні операції / стаціонар без операцій / інсульт / інфаркт; назви за `package_id` ще не підтверджені довідником «Опис атрибутів наборів даних.xlsx») ≈ **28,4 млн грн**, усього по ЛШМД — 31,5 млн. Наша оцінка вартості липневих епізодів — 23,9 млн, втрат — 4,3 млн (≈ 15% фактичних виплат за стаціонар) — **верхня межа**:
- 100% втрат для «виписку не передано» ймовірно завищено — частину передають пізніше;
- у 2026 р. частина оплати — глобальна ставка з обсягів квітня–вересня 2025 р. (п. 35–36, коефіцієнт частки 0,45), тож помилки б'ють по змінній частині і по базі бюджету на наступний рік, а не по всій сумі одразу.

Порядок оновлення виплат НСЗУ — двічі на місяць; за поточний місяць спершу є лише аванс.

**Дані** — `lpz.lpz_case_quality_snapshot`, один рядок на випадок (`helsi_case_id`). Між прогонами зберігаються `first_flagged_at` / `resolved_at`, тож видно, що виправили. Персональні дані пацієнтів не зберігаються — id пацієнта використовується лише в браузері для пошуку накладок.

### Нагадування лікарю по відкритих епізодах (21.09.2026)

У звичайному кабінеті лікаря (`doctor-cabinet.html`) у полі «Перебуває у відділенні» є вкладка **«Нагадування · N»**: відкриті пацієнти лікаря, у яких **від 3-ї доби** перебування (доба = цілі доби + 1) є що дооформити. Для кожного — що виправити (з підказкою й посиланням «виправити в helsi»), «триває N дн.» по кожній проблемі, «запис не змінювався N дн.», доба перебування й норма діагнозу; завідувачу передається (`escalate`), коли перебування довше за 75-й перцентиль по діагнозу (діагнози без норми — з 10-ї доби). «М'які» пункти (`single_diagnosis`, `injury_no_external_cause`, `no_doctor` — доведено, що оплату не блокують; `SOFT_REMINDER_CODES`) у лічильник і ескалацію не входять: епізоди лише з ними показуються нижче під підзаголовком «Менш важливе». `no_interventions` лишено важливим: серед розрахованих епізодів без кодів втручань відмов НСЗУ 18,9% проти 12,0% у решти, середня вага ДСГ 0,92 проти 1,67 (частково через те, що хірургічні випадки природно мають втручання, тож причинність не доведена). На прогоні 21.09.2026: з 662 відкритих епізодів нагадування 321 → важливих 90, лише м'яких 231, ескалацій 39.
- **Правило й норми:** `lib/quality-access.js` (`buildReminder`, `getLosNorms`); `/api/lpz-case-quality?reminders=1` додає `reminder` до відкритих епізодів. Норми перебування — медіана й p75 по перших 3 символах МКХ з `lpz_hospitalizations` (з 2023 р., 258 діагнозів, кеш на добу); офіційних нормативів тривалості НСЗУ не публікує (постанова №1808 п.36/38: референтні значення = середнє по ДСГ за кв.–вер. 2025 ÷/× 3 або 1,5, самі цифри — алгоритм НСЗУ).
- **Відстеження змін між прогонами** — у наявному полі `hints.__track` (без нових колонок): `fp` (відбиток діагнозів/втручань/лікаря/виписки), `changed_at`, `first_seen` по кожній проблемі, `fixed` (виправлені з датою). Пишеться в `local-quality-ingest.js`; перший прогін після змін лише ініціалізує історію (`first_seen` береться з `first_flagged_at`).
- **Щоденний швидкий прогін** (щоб нагадування були актуальними): у helsi-вкладці `runQualityDaily({ org: '43342788', closedSince: '<3 дні тому>' })` — усі відкриті + щойно закриті, кілька хвилин.

### Щоденний прогін

Автоматичного доступу до helsi поки немає, тому прогін ручний:

1. Запустити локально `npm run dev` (маршрут `/api/local-quality-ingest` працює лише в dev, на проді — 404).
2. Увійти в [helsi.pro](https://helsi.pro) у браузері.
3. У консолі вкладки helsi вставити вміст `scripts/helsi_quality_daily.js` і виконати:
   ```js
   runQualityDaily({ org: '43342788' })              // закриті — з 1-го числа попереднього місяця
   runQualityDaily({ org: '43342788', closedSince: '2026-07-01' })  // довший період
   ```
4. Прогрес — `window.__qd` (`stage`, `detailed`/`total`, `result`, `err`).
5. Сесія helsi часто завершується посеред прогону (`err: "Сесія helsi завершилась…"`). **Увійти знову в іншій вкладці** (не перезавантажувати робочу) і в робочій вкладці викликати `runQualityDaily` з тими самими параметрами — уже зібрані епізоди не перезапитуються.

Повний прогін ЛШМД за 2026 рік (`closedSince: '2026-01-01'`, ≈6,9 тис. епізодів, по 3 запити на епізод) — близько 15 хв; щоденний коротший.

**Скільки даних є в helsi.** Модулем «Стаціонар» (`encounter_cases`) ЛШМД користується приблизно з середини травня 2026: виписаних у січні–квітні — 0, у травні — 73, у червні — 1 841. Госпіталізації за ранні місяці в каноні `lpz` прийшли з карток helsi, а не з епізодів стаціонару, тож для контролю записів їх немає. Список `encounter_cases/?status=closed` без фільтра віддає лише наявні ≈6,6 тис. записів (`has_next: false`). Фільтри за датою, які використовує сам інтерфейс helsi: `discharge_start` / `discharge_end`, `hospitalization_start` / `hospitalization_end` (формат `YYYY-MM-DD`); кількість — `encounter_cases/count/?…`.

### Фінансовий режим кабінетів (клік на емблему)

Ті самі сторінки, пігулки періоду (рік / місяць / день) і графіки, але замість звичайних показників — контроль записів. Кожна сторінка відкривається у звичайному вигляді; клік на емблему перезавантажує саме цю сторінку з `?fin=1`, повторний клік — без нього (`utils.js:isFinanceMode` / `wireFinanceEmblem`). Режим **не** переноситься на інші сторінки — окрім переходів власника сайту всередині фінансового режиму (головна → відділення → лікар додають `fin=1`).

| Сторінка | Хто може ввімкнути | Що показує |
|---|---|---|
| `entry.html` | власник сайту, головний лікар | шапка й блоки напрямків: **зароблено** · врятувати · втрачено (грн) · % з помилками · епізодів (+ відкриті з зауваженнями) |
| `head-cabinet.html` | завідувач (своє відділення), власник сайту | плитки й графіки відділення; праве нижнє поле замість «Перебуває у відділенні» — **короткий список «ПІБ пацієнта — ПІБ лікаря — ⚠ кількість зауважень»**; клік на лікаря: завідувачу — фільтр списку, власнику — перехід у кабінет лікаря (`fin=1`); шапка — уся лікарня (`level=hospital`, без грошей для завідувача) |
| `doctor-cabinet.html` | лікар (свої епізоди), власник сайту | плитки й графіки лікаря; праворуч — картки епізодів з ПІБ пацієнта, первинною/вторинною підказкою, «виправити в helsi» і сумами (лише власнику); свій рядок в Ординаторській виділено й прокручено в кадр |

- **Категорії:** правильні — закриті без зауважень; поправимі — із зауваженнями, строк (`fix_deadline`) ще не минув; непоправимі — строк минув. Закриті відносяться до періоду за датою виписки (Київ), відкриті — лише коли період містить сьогодні.
- **Гроші** (власник сайту й головний): **«Зароблено»** = вартість правильних + (вартість − ризик) епізодів з помилками; «врятувати» / «втрачено» — ризик поправимих / непоправимих (`*_price`, `*_risk`). Завідувач і лікар — лише кількість. Оцінка за тарифами НСЗУ, не фактична виплата.
- **Графіки:** гістограма — стовпець = усі епізоди (у власника — їхня вартість), знизу червоне — непоправимі, над ним бурштинове — поправимі (`bar-chart.js`: `y_lost` поверх `y_urgent`, клас `.fin-chart`); хвиля — кількість епізодів з помилками (червона) / правильних (синя), **в одному масштабі від нуля** (`wave-chart.js: sharedScale`). Клік на рік → місяці → дні, клік на день звужує плитки й список.
- **Вигляд:** темна графітова тема й напис «Фінансовий режим» (`.slide.fin-mode`, `layout.css` — перевизначені кольорові змінні й кілька жорстко заданих кольорів); обраний лікар в Ординаторській — смужка й колір акценту (`head-cabinet.css: .doc-active, .own`).
- **ПІБ:** `/api/lpz-case-quality?names=1` — ПІБ пацієнта з `lpz_hospitalizations` (`helsi_record_id = helsi_case_id`) і лікаря з `lpz_empl`, у межах обсягу користувача; у самій таблиці перевірки персональних даних немає. Епізоди, яких ще немає в каноні, — з номером картки.
- **Посилання в helsi:** «виправити в helsi ↗» біля кожного зауваження веде в розділ епізоду (`tabName=MAIN` — діагнози, послуги, процедури, лікар; `tabName=CHRONOLOGY&type=discharge` — виписка; `tabName=LIST_TRANSFERS` — накладки); усі посилання відкриваються в одній вкладці (`target="helsi"`). Перевірено на живих епізодах 14.09.
- **Дані й швидкість:** `/api/lpz-quality-finance?org=&year=&month=&day=&dept=|doctor=|direction=&level=` → `{ kpi, trend[] }`; `/api/lpz-case-quality` віддає лише епізоди із зауваженнями + `total_checked`. `lib/quality-access.js`: правила доступу, кеш таблиці перевірки в пам'яті на 5 хв (порції PostgREST паралельно; відділення/лікар читають лише свої рядки, якщо лікарня ще не в кеші; плитки — легкі колонки без підказок); `local-quality-ingest` скидає кеш. Швидкі перемикання пігулок — малюється лише відповідь на останній запит (`FINANCE_REQUEST_SEQ`). Картка епізоду — `public/js/quality-notes.js` (спільна з `quality.html`).
- **Без «розового спалаху»:** слайд прихований, доки не застосовано кольори лікарні (`html.theme-ready`), остання схема кешується в браузері (`localStorage: lpzHospitalTheme`), запобіжник 3 с; кабінети, що дізнаються лікарню після `/api/me`, ставлять `window.HOSPITAL_THEME_PENDING = true`.

### Факти епізодів і каталог перевірок (`admin-episode-facts.js`)

Дослідницька сторінка, окрема від `quality.html`: не готові висновки (flags/warnings), а **сирі факти** епізоду + перевірка кожного правила коректності на реальних даних helsi (`package-validation`, ЕСОЗ-статус), щоб знати напевно — впливає конкретна помилка на оплату НСЗУ чи ні. Клік на рядку таблиці **розгортає повний епізод інлайн** (діагнози, втручання, пакет/ДСГ/ціну, fin-повідомлення package-validation) — не переходить у helsi; посилання «відкрити в helsi ↗» окреме, всередині розгортки.

**Дані:**
- `lpz.lpz_episode_facts` — 41 поле на епізод: діагнози за ролями (основний/супутній/ускладнення), зовнішня причина травми, втручання, `injury_type`, стан ЕСОЗ, і повний результат `package-validation` (пакет/ДСГ/вага/ціна/фактична оплата/fin-повідомлення). Станом на 2026-09-18: **1608 епізодів травматології ЛШМД** (обидва відділення, відкриті+закриті, з 04.05.2026) — зібрано `scripts/collect_lpz_episode_facts.js`; з них **1448 пройшли `package-validation`** — `scripts/collect_package_validation.js`.
- `lpz.lpz_quality_check_catalog` — каталог перевірок: код, назва, `blocks_payment` (так/ні/невідомо), доказ і метод перевірки, кількість епізодів. Джерело правди для розділу нижче.
- Завантаження в базу — два локальні dev-only ендпоінти (як і `local-quality-ingest.js`, працюють лише на `localhost:3000`, вимкнені на проді): `pages/api/local-episode-facts-ingest.js` (нові сирі епізоди — звичайний `insert`, не `upsert`) і `pages/api/local-package-validation-ingest.js` (лише цінові поля — точковий `UPDATE` по кожному рядку, **не** `upsert`, з причини нижче).

**Формула ціни (розшифровано 2026-09-18, з повного тексту постанови №1808, не з вебу):** тариф = глобальна ставка (фіксована на весь 2026 рік з обсягів квітня-вересня 2025, вага 0,45, п.36(1)) + ставка на пролікований випадок (вага 0,55, п.38(1) — це і є `adjustment_coefficient` з `package-validation`, завжди 0.55, однаковий для всіх епізодів). Помилки поточних епізодів впливають лише на 55%-ву змінну частину цього місяця; 45% вже заморожено на 2026 рік, але поточні показники стануть базою для глобальної ставки **2027**.

**Каталог перевірок — повний стан на 2026-09-18** (травматологія, усе перевірено живими викликами `package-validation` — POST `.../encounter_cases/{id}/encounters/{id}/package-validation/`, той самий недокументований ендпоінт, яким рахує сама форма виписки):

| Перевірка | Блокує оплату | Доказ (коротко) |

**Коефіцієнти package-validation — розшифровано й вичерпно підтверджено на даних (2026-09-18).** У травматології зустрічаються рівно 4 типи (перевірено по всіх успішних валідаціях — інших немає):
- **ААС=0.6** (77 епізодів) — п.38(13) постанови №1808, коефіцієнт до ВАГИ КОНКРЕТНОГО ЕПІЗОДУ (не бюджету лікарні, як спершу здавалось), недокументований алгоритм НСЗУ рівня діагноз+втручання. Не залежить від якості документування — навіть еталонний правильно заповнений епізод отримує його. Трапляється і в багатоденній хірургії (пакет №3), і в одноденній (№47), навіть у межах ОДНОГО ДСГ-коду частина епізодів отримує його, частина ні.
- **Коефіцієнт за тривалість** (52 епізоди, значення 0.05–0.36, «мінімальна тривалість» 2–5 діб залежно від ДСГ) — п.36(6-7)/38(9-10): якщо LOS менший за нижнє референтне значення ДСГ (середнє по всіх лікарнях, квіт-вер 2025, ÷3 або ÷1,5 для 10 конкретних кодів), замість повної ваги рахується `базовий_коефіцієнт_за_добу × дні`.
- **Множинні операції** (23 епізоди) — п.38(11): 100% ваги найбільшої операції + 75% наступної + 60% решти.
- **За планову допомогу=0.8** (4 епізоди) — п.36.8/38(12), вже враховано в `lib/quality-pricing.js`.

Номери пакетів підтверджено: **№3** — багатоденна хірургія, **№4** — без операцій, **№47** — хірургія одного дня.

**Технічні пастки, знайдені й виправлені:**
- `doctor_id` у зібраному JSON — внутрішній `care_manager.id`, не `helsi_id`/`resource_id`, яким проіндексовано `lpz_empl`. Виправлено зіставленням за ПІБ (44 унікальних лікарі) з розв'язанням колізій імен через `position_name`.
- Supabase/PostgREST повертає максимум 1000 рядків незалежно від `.range()` (`db-max-rows`) — API (`pages/api/lpz-episode-facts.js`) сторінкує запит вручну.
- **Payload `package-validation`:** `admit_source`/`discharge_disposition` — лише `.id` (число), не весь об'єкт («очікувалось значення первинного ключа, отримано dict»); `division` — лише UUID-рядок; `priority` іноді порожній рядок `""` у сирих даних — API вимагає `null`. `package` можна не надсилати — ендпоінт сам визначає правильний пакет.
- **Postgres + upsert:** `INSERT ... ON CONFLICT DO UPDATE` перевіряє NOT NULL-колонки (`admission_at` тощо) для INSERT-гілки ще до перевірки самого конфлікту — частковий upsert (лише цінові поля) падає на NOT NULL, навіть якщо рядок точно вже існує. Тому цінові поля оновлюються звичайним `UPDATE` (`local-package-validation-ingest.js`), не `upsert`.
- **Інцидент 2026-09-18:** `.in()`-запит на 500 UUID у перевірці «чи рядок вже існує» мовчки провалився (result не перевірявся на `error`) → усі рядки хибно визнались новими → повний upsert цінові поля обнулив. Відновлено з `window.__pvSlim`, що ще жила в пам'яті вкладки браузера. Виправлено: батч 200, будь-яка помилка перевірки — abort, запис нових рядків — звичайний `insert` (не `upsert`), падає на дублікаті замість тихого перезапису.
- Пагінація `encounter_cases` зі зсувом (`skip`) під час зміни статусу епізоду (open→closed) під час збору інколи дублює рядок — дедуплікація за `helsi_case_id`.
- `card_number` не унікальний у часі — різні епізоди різних періодів можуть мати однаковий номер картки; унікальний лише `helsi_case_id`.
- Клік на рядку таблиці → розгортка інлайн (було: `window.open` в `https://helsi.pro/hospital/cases/{helsi_case_id}?tabName=MAIN`) — той самий URL лишився кнопкою «відкрити в helsi ↗» всередині розгортки.

Доступ — лише власник сайту (`is_owner`), як і `admin-status`/`admin-hospitals`.

**Джерела:** [Постанова КМУ №1808 від 31.12.2025](https://zakon.rada.gov.ua/laws/show/1808-2025-%D0%BF) (повний текст — друкована версія `/1808-2025-п/print`, звичайна сторінка не віддає текст WebFetch, SPA); дані `payments_on_contracts_pmg_2026.csv` на [data.gov.ua](https://data.gov.ua/dataset/25a46db9-2f15-4302-9b59-9bd761c80f46) оновлюються **щотижня** (не «двічі на місяць», як було записано раніше) — графік самих виплат НСЗУ в постанові не описано.
