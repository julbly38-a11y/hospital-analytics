Проєкт: `hospital-analytics-qwerty` (гілка `qwerty-project-connection-e6mjy9`, Supabase `nobodyjul` = `ubjnztanehqlsrqphdqy`, прод `https://nobodyjul.vercel.app`). Попередній handoff: `README_HANDOFF_2026-09-24.md` (там і далі актуальні розділи про вечірній скрипт, чистку, безпеку, автодеплой). Старий проєкт `hospital-analytics` / `nobodybly.org` не чіпати, гілку в `main` не зливати.

## 1. Що змінилось (коротко)

- Ранковий скрипт тепер працює для кількох лікарень: `--org <ЄДРПОУ>` (ЛШМД за замовчуванням, Хотинська ЦРЛ `02005875`). Перший справжній прогін Хотина зроблено.
- Завантаження сирих даних у БД: пряме `psql \copy` в одній транзакції (≈18 с замість кількох хвилин), відсів дублів, автододавання нових колонок.
- Виправлено три втрати даних у каноні: записи з друкарськими помилками в номері картки, результат лікування лише для статусу `closed`, дубль одного `id` у списках helsi.
- Захист від запису не в ту лікарню: перед будь-яким вивантаженням скрипт перевіряє, чия це сесія helsi.
- Автоперезапуск вивантаження, якщо вкладка helsi втратила стан (перезавантажилась після входу).
- Кнопка «Розмити ПІБ» для власника сайту.

## 2. Цикл helsi → lpz для кількох лікарень

| Лікарня | ЄДРПОУ | Команда | Вікно Chrome |
|---|---|---|---|
| ЛШМД | 43342788 | `python3 scripts/helsi_sync.py` | профіль `helsi-sync-chrome`, порт 9333 |
| Хотинська ЦРЛ | 02005875 | `python3 scripts/helsi_sync.py --org 02005875` | профіль `helsi-sync-chrome-02005875`, порт 9334 |

- Довідник лікарень — `ORGS` у `scripts/helsi_sync.py` (назва, папка даних `raw/<лікарня>`, порт і профіль Chrome, ліміт епізодів, таймаут, типи епізодів, дата відсікання). Нову лікарню додають одним записом; без запису в `ORGS` скрипт не працює.
- **Запобіжник сесії:** `/api/user/me → organization.edrpou`. Якщо сесія належить іншій лікарні (або організацію не вдалось визначити), скрипт зупиняється до вивантаження, нічого не записавши. Працює й для вечірнього скрипта (через `acquire_tab`).
- Для не-ЛШМД лише транспорти `cdp` / `applescript` (потрібна вкладка для перевірки організації).
- SQL-кроки `raw_to_canon_*.sql` написані під ЛШМД; для іншої лікарні `render_sql` підставляє ЄДРПОУ. Правило виключення квітня–травня 2026 стосується **лише ЛШМД** і на інші лікарні не діє. Нове ЛШМД-специфічне правило в SQL обовʼязково додавати в `LSHMD_ONLY_SQL_LEFT`, інакше воно діятиме й на інші лікарні (захист ловить лише зайву копію правила відомої форми).
- `verify`: перевірка квітня–травня лише для ЛШМД; решта, включно з періодом з 01.07.2026 («записів helsi з 01.07.2026, яких нема в каноні» має бути 0), для всіх.
- Лог: `~/Documents/LSMD/logs/helsi_sync_<мітка>_<дата>.log` (для Хотина мітка `khotyn_`).
- Вечірній скрипт `helsi_evening.py` лишається **лише для ЛШМД**.

### Як працювати з акаунтом helsi
- Один акаунт має доступ до двох організацій (ЛШМД і Хотин), перемикання: іконка лікаря вгорі праворуч у helsi. Перед запуском для Хотина перемкнути на «Хотинську». Якщо вибрана інша лікарня, скрипт зупиниться з поясненням.
- Імовірно, один акаунт = одна активна сесія: вхід у друге вікно, схоже, завершує сесію в першому (спостерігалось 01.10, не доведено). Після входу в одне вікно інше може потребувати повторного входу.
- **Під час вивантаження не відкривати й не перезавантажувати вкладку helsi** у вікні скрипта: це обнуляє стан. Автоперезапуск (до 3 разів) страхує, але прогін починається спочатку.
- Вивантаження живе у вкладці; якщо скрипт упав за таймаутом, повторний запуск **підхоплює те саме вивантаження** (`already running`), доки вкладку не закрито й не перезавантажено.

## 3. Надійність завантаження сирих даних

`scripts/load_json_raw.py`:
- пряме `psql \copy` в одній транзакції (DELETE + COPY + перевірка кількості); обрив зʼєднання більше не лишає таблицю напівзаповненою; без `psql` або з `HELSI_RAW_LOADER=rest` — старий шлях через PostgREST з повтором файлу;
- відсів повністю ідентичних дублів (helsi віддає сторінки зі зсувом, ~600 з 16 тис. епізодів ЛШМД приходять двічі); однаковий `id` з різним вмістом лишається й дає попередження;
- автододавання нових `text`-колонок у `lpz_raw_*` (helsi час від часу додає поля; запобіжники: лише `lpz_raw_*`, лише безпечні імена, лише `text`; вимкнути `HELSI_RAW_AUTO_COLUMNS=0`). Раніше це зупиняло весь прогін.

## 4. Виправлення в каноні (`scripts/sql/`)

- `raw_to_canon_hospitalizations.sql`: записи з нестандартним номером картки (`№12566`, `1`5399`) більше не відкидаються, а отримують технічний `id_case` (850 000 000+); `helsi_no` = лише цифри, оригінал у `lpz_raw_*.number`. У стейджингу **один рядок на helsi `id`** (`DISTINCT ON`, закритий має перевагу над відкритим, далі найсвіжіший `last_updated_at`); без цього дубль з різним вмістом валив `ON CONFLICT`.
- `helsi_sync_extract.js`: результат лікування збирається за статусами `closed`, `registered`, `pending_registration`, `on_discharge` (після виписки випадок проходить ці статуси, `closed` останній). Раніше `status=closed` лишав ~320 виписаних випадків без результату (ЛШМД: закритих 2026 без результату було 83, стало 24).

Це ≈26 тис. епізодів за 6–7 хв замість годин. Епізоди без `lastEncounterAt` (кінець списку, невпорядковано) не беруться. Ліміт епізодів 250 000, таймаут 2 год.

- **Якість даних Хотина (самі дані helsi, не помилка скрипта):** без відділення 90,7 %, без лікаря 90,3 %, закритих без результату лікування 3 501 із 8 087 (43 %), виписка раніше за госпіталізацію 15 записів. За інструкціями helsi відділення вимагає налаштованого стаціонару (перелік відділень, профілі ліжок, закріплення персоналу) і кроку «розміщення пацієнта»; найімовірніша причина, що це не зроблено, але налаштування Хотина не перевірялись.

- У `--dry-run` сирі таблиці **не вантажаться**, тому пробний прогін канону йде по старих сирих даних.
