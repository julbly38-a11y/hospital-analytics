## Що робить entry.html

Сторінка, куди редіректить після логіну з `layout.html`. Захист на клієнті: `fetch('/api/me')`, немає ролі → назад на `/layout.html`. `org_edrpou` для сторінки береться з сесії користувача (`empl.org_edrpou` через `app_users.empl_name_id`), **не** з URL-параметра, як на `layout.html`.

Два незалежні шари в `#slideRoot` (`entry.js`):

2. **`renderClinicalBlock`** — зліва два вертикально-скрольовані списки клінічних відділень: терапевтичний зверху, хірургічний знизу, без підписів блоку. Дані з нового `/api/lpz-departments` (`lpz.lpz_departments`, фільтр `direction IS NOT NULL`)

### Чергові лікарі — ТЕСТОВИЙ РЕЖИМ

Новий `/api/lpz-duty-doctors` — **реального графіка чергувань у lpz-моделі ще немає**. Тимчасово: по одному лікарю (`role='doctor'`, перший за алфавітом прізвища) на кожне клінічне відділення. Явно позначено коментарем у файлі. Повертає `doctor` (Прізвище + 2 ініціали для показу), `doctorFull` (повне ПІБ) і `position` — для тултипу.

**Відомий нюанс, не досліджений до кінця:** користувач помітив, що "Рябий" і "Блинду" в реальності працюють в одному відділенні (неврологічне/інсультне), а тестовий алгоритм розкидав їх по різних — це очікувано для тестової заглушки (перший лікар за алфавітом на "домашнє" відділення з `lpz_empl.department_structure_id`, не реальна ротація чергувань), просто зафіксовано як подальше зʼясування, коли зʼявиться справжнє джерело даних чергувань.

### Перехресна підсвітка лікар↔відділення

`wireDeptHover`/`wireDutyHover` в `entry.js` — **живий пошук елементів у момент наведення**, НЕ кешування NodeList на старті (на відміну від старого `utils.js:initCrossHighlight`, який для async-контенту цієї сторінки не працює — залишений недоторканим, бо може використовуватись іншими сторінками). Дані узгоджені через `data-dept`/`data-home` атрибути з однаковими (скороченими) назвами відділень.

### Тултип при наведенні на лікаря

Показує повне ПІБ + посаду (відділення прибрано з тексту — воно тепер показується підсвіткою, не дублюється текстом).

## Скролові списки — уніфікована інфраструктура (`public/js/utils.js`)

За проханням користувача "стиль списків повинен бути однаковим у будь-якому списку" — спільна логіка винесена з `entry.js` у `utils.js`, щоб будь-яка майбутня сторінка (напр. список пацієнтів на `head-cabinet.html`) могла підключити без дублювання коду:

- **`enableDragScroll(el, axis)`** — прокрутка перетягуванням мишею (`axis='x'`/`'y'`) з **інерційним гальмуванням** після відпускання (розраховує швидкість руху перед відпусканням, гальмує з коефіцієнтом тертя 0.94 через `requestAnimationFrame`)
- **`updateFadeMask(el, axis)`** — fade-маска на живих краях списку (зникає з того боку, де прокручувати вже нікуди — щоб не затуляти перший/останній пункт)
- **`fitHeightTo(el, bottomPx, gap)`** — динамічна максимальна висота елемента, рахується з реального `offsetTop`, **не хардкод** (на відміну від старого еталону `.docs-list { max-height: 215px }` з `docs/CABINET_HANDOFF.md`, який був жорстко заданим числом)

`entry.js` використовує ці функції для обох напрямків: `duty-docs` (горизонтально), `dept-list`/`dept-list2` (вертикально, замінили попередній підхід "зсунути смугу вниз, якщо список задовгий" — `fitDeptListHeights` тепер обмежує список фіксованою висотою + скрол замість зсуву сусідніх елементів).

**Побічний ефект, на який натрапили й виправили:** `overflow-y: auto` за специфікацією CSS автоматично активує і `overflow-x` (не можна лишити одну вісь `visible`, коли інша не `visible`) — через це довгі назви відділень, які раніше "вибігали" за межі блоку зліва (при `white-space: nowrap`), почали обрізатись. Виправлено розширенням блоку (`left: 20px; width: 545px` замість `left: 153px; width: 380px`) і поверненням `white-space: normal` (перенос рядка).

## Per-лікарня кольорова тема — `lib/hospital-themes.js`

Користувач захотів, щоб вигляд сторінки (кольори, mesh-фон) відрізнявся для ЛШМД і Хотина, орієнтуючись на кольори їхніх емблем (`public/logos/khotyn.svg` — растровий base64 PNG всередині SVG, без явних fill-кольорів; `public/logos/lsmd.svg` — чистий вектор, `#9cb1d8`/`#4e73b9`).

**Підхід (узгоджений з користувачем після обговорення двох варіантів):** ручний підбір кольорів під кожну лікарню (не автоматичний аналіз пікселів — для растрового Хотинського лого це було б ненадійно), збережений як мапа `edrpou → theme` в `lib/hospital-themes.js`.

- **Хотин НЕ має запису** в цій мапі — він і є дефолтна схема, вже прописана в `public/shared/theme.css`. Це задумано як явний fallback-механізм: **немає запису для лікарні → застосовується дефолт Хотина**.
- **ЛШМД** має повний набір override: `--c-ink-1..4`, `--c-sage`, `--c-taupe`, `--c-taupe-light`, `--c-accent-berry`, `--c-accent-pink`, `--c-cream` (усі — холодні синьо-сірі тони) + 5 змінних `--mesh-1..5` (кольори плям анімованого mesh-фону).

**Механізм застосування:**
1. `pages/api/hospital-info.js` — тепер повертає поле `theme` (`getHospitalTheme(edrpou)`, `null` якщо немає запису)
2. `public/js/utils.js` — нова `applyHospitalTheme(theme)`, викликається з `initHospitalName()` (яка й так уже фетчить `/api/hospital-info` на кожній сторінці з лого/назвою) — накладає CSS-змінні на `:root` через `style.setProperty`
3. `public/shared/entry.css` — mesh-фон (`.bg`/`.bg2`) переписаний на `var(--mesh-N, дефолт-Хотина)` — без переопределення з JS показує теплі тони Хотина за замовчуванням

Перевірено в браузері: ЛШМД → синя схема + синій mesh; Хотин → без жодних змін. **`layout.html` цю тему поки не підключає** (там немає mesh-фону взагалі — `entry.css` підключений лише до `entry.html`), і не обговорювалось, чи розповсюджувати theme-механізм і туди.
